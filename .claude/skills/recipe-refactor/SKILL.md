# DaerD Recipe の意味的リファクタリング

自動生成された呼び出し列を、レイヤーごとのメソッド・パラメータクラス・データテーブル・
ループへ整理する。**出力される AnimatorController が元と完全に一致すること**が絶対条件で、
読みやすさはその次。

## どのファイルを触るか

エクスポートは partial class を 2 つに分けて出力する:

| ファイル | 持ち主 | 中身 |
|---|---|---|
| `<Name>.Generated.cs` | DaerD | `[SerializeField]` フィールドと `BuildGenerated(...)`。エクスポートのたびに丸ごと再生成される。**読む専用** — 編集しても次のエクスポートで消える |
| `<Name>.cs` | ユーザー / AI | 実際に実行される `Build(...)`。DaerD は二度と上書きしない。**リファクタはここへ書く** |

初期状態の手編集側は次の 1 行だけ。これを、`BuildGenerated` の呼び出し列を整理したコードで
置き換える:

```csharp
protected override void Build(ControllerBuilder c) => BuildGenerated(c);
```

`BuildGenerated` は消さない・改名しない・手編集側から再定義しない。比較の基準であり、
次のエクスポートで作り直される側だから。

`<Name>.Generated.cs` が存在しない Recipe は分割前の旧レイアウト（1 ファイルに
フィールドと `Build`）。その場合はそのファイルを直接整理するか、先に DaerD から
再エクスポートして 2 分割へ移行する（移行時は旧ファイルが `.cs.bak` に退避される）。

## 進め方

1. `<Name>.Generated.cs` を通しで読み、レイヤー構成と各レイヤーの役割を把握する
   （ステート名・パラメーター名・遷移条件から推測する。分からない役割は推測をコメントに
   書かず、構造の整理だけに留める）。冒頭に API チートシートがある。
2. リファクタ後の骨格を決める: `Build` はレイヤーごとのメソッド呼び出しだけにする。
   複数レイヤーから使うパラメーターハンドルは `Params` クラスに集める。
3. 下の不変条件を守りながら、手編集側 `<Name>.cs` に書く。
4. 最後に検証手順をユーザーに案内する（Compare → Generate → Verify）。

## 不変条件（破ると挙動が変わる／Compare・Verify が乖離を報告する）

- **生成順 = Animator の並び順**。以下の順序は元コードと同一に保つ:
  - パラメーター宣言の順（パラメーター一覧の順になる）
  - レイヤー作成の順（レイヤーの重ね順）
  - 1 つのステートマシン内での `NewState` / `NewSubStateMachine` の順
    （最初のステートが default。ステート一覧のインデックスにもなる）
  - **同じ遷移元からの遷移の順**（評価優先度そのもの）。`AnyTransitionsTo` /
    `EntryTransitionsTo` / `TransitionsTo` / `Exits` を張る順を元と揃える。
    遷移元が異なる遷移同士の順序だけは自由に並べ替えてよい
  - 1 ステート内のビヘイビアの順、1 遷移内の `When`/`And` 条件の順。
    ステートマシンに付いた Behaviour（`main.BehaviourJson(...)` / `sub.BehaviourJson(...)`）は
    **どのマシンに付いているか**を取り違えないこと。ステートの Behaviour とは別物
  - テーブル化するときは行の並び = 元の生成順。並びが不規則でも「元データどおり」と
    コメントして保存する
- **`[SerializeField]` フィールドは Generated 側にある**。手編集側で再宣言しない
  （二重定義になる）。同じ partial class なので名前でそのまま参照できる。名前の変更も
  不可（Recipe アセット側の参照キー）。手編集側で足す独自フィールドは自由。
- **`BehaviourJson` の JSON 文字列は 1 文字も変えない**（`m_ObjectHideFlags` 以外は
  厳密比較される）。ヘルパー関数化するときも連結結果が元の文字列と一致すること。
- **後段ステップ（`c.Gadgets(...)` / `c.AsyncSync(...)` / `c.Raw(...)`）は呼び出しの
  順序と引数をそのまま保つ**。これらは IR に載らないので Compare も Verify も見逃す。
  特にガジェットは宣言順に適用され、後のガジェットが前の出力を入力にできる（並べ替えると
  「入力が存在しない」で落ちる）。レイヤー名がそのガジェットレイヤーの同一性そのもの。
- 数値はそのまま保つ。`0.125f` を「約 0.1」に丸めるなどは不可。定数化は値が同一なら可。
- `.Default()`・`WithTransitionToSelf()`・`DrivingLocally()` などの有無を落とさない。
- パラメーターの既定値付き宣言 `c.FloatParameter("X", 1)` と無し宣言は区別を保つ
  （無しは「参照のみ」で、Generate 時に既定値を上書きしない）。

## 推奨する整理パターン

- `Build` → `DeclareParameters` + `Build<レイヤー名>Layer` ×N。
- `sealed class Params { public BoolParam ...; }` に複数レイヤーで使うハンドルを集約。
  宣言だけで使わないパラメーターは変数に取らない。
- 同型ステートの量産は行 struct + テーブル + ループへ（例: ジェスチャー表情 8 セット）。
  行に載せるのは「変わるものだけ」（クリップ・座標・閾値・駆動値）。
- 繰り返す遷移条件はヘルパーメソッドへ（例: `EnterMmdMode(t, p)`）。
- 連番パラメーター（`New Float 1..5` 等）は配列 + ループへ。
- マジックナンバーは `const` へ（ジェスチャー番号、ブレンド時間、スロット数など）。
- レイヤーごとに `/// <summary>` で役割を 1〜3 行説明。クラス先頭にレイヤー一覧の要約。
- 座標は行データに載せるか、元のまま layout 節に残す。どちらでも良いが混在させない。
- DBT ガジェットのレイヤーが生の巨大ツリーとして出力されている場合は、`c.Gadgets(...)` の
  呼び出しへ書き換えられることがある（生成側にその旨のコメントが付く）。ただし**同じツリーに
  なる保証は無く Compare も通らない**ので、ユーザーに確認してから行い、Generate 後の
  実挙動で確かめる。

## 検証（必ず案内する）

1. Recipe アセットの **「エクスポート側と比較」(Compare)** — `Build` と `BuildGenerated` が
   宣言する内容を IR レベルで突き合わせる。コントローラーには一切触らないので最初に回す。
   ここが「一致」なら、整形は意味を変えていない（読み方ではなく出来上がる物の比較なので、
   ループやテーブルへの書き換えでも通る）。
2. **Generate**（対象は複製したコントローラーが安全）→ **Verify** で実物との乖離ゼロを確認。
3. 後段ステップ（Raw / 巡回同期 / DBT ガジェット）は Compare にも Verify にも出ない。
   そこだけは生成側と手編集側を目視で突き合わせる。
4. 乖離が出たら報告内容（レイヤー/ステート/フィールド名）から順序・値の取り違えを探す。

元ファイルのコピーを取る必要は無い — `<Name>.Generated.cs` が常に手つかずの基準として
残る（旧レイアウトの 1 ファイル Recipe を直接整理する場合のみ、事前にコピーを残すこと）。

## 再エクスポートへの追従

コントローラー側を編集して再エクスポートすると、変わるのは `<Name>.Generated.cs` だけで、
整形済みの手編集側はそのまま残る。差分の取り込みはこの順で:

1. `git diff -- <Name>.Generated.cs` を読む（これが「前回エクスポート以降にコントローラーで
   何が変わったか」のレポートになる）。
2. 同じ変更を手編集側の構造へ反映する — テーブル化してあれば行の追加・修正で済むことが多い。
   構造を作り直す必要は無い。
3. Compare で一致を確認する。
